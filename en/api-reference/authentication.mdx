The Bridger Gateway accepts two authentication headers. Send just one of them.

```http
x-api-key: dk_live_xxx
Authorization: Bearer dk_live_xxx
```

## Issuing an API Key

Issue/revoke keys on the **Auth keys** page at [portal.bridger.kr](https://portal.bridger.kr).
See the [API key guide](/en/guides/api-keys) for the full flow.

## Authentication failure response

If the key is missing or invalid, **401 Unauthorized** is returned. The body is
not JSON but a `text/plain` error code, and an RFC 6750-style
`WWW-Authenticate` challenge header is sent along so OAuth clients can find the
authorization server and scopes.

```http
HTTP/1.1 401 Unauthorized
Content-Type: text/plain; charset=utf-8
WWW-Authenticate: Bearer error="invalid_token", resource_metadata="https://mcp.bridger.kr/.well-known/oauth-protected-resource/mcp"
```

```text
invalid_token
```

`resource_metadata` points to the RFC 9728 protected-resource metadata and
echoes the requested MCP endpoint path (`/mcp`). Read the authorization server
(issuer) and supported scopes from it, then start the
[OAuth 2.0](#oauth-20) authorization-code + PKCE flow. A valid token that lacks
the required scope is rejected with the same challenge form as
**403 Forbidden** (`Bearer error="insufficient_scope",
resource_metadata="...", scope="..."`).

## Tenant identification

A tenant is identified **by API Key only**. A key issued at the organization level is automatically
linked to that organization's tenant.

<Warning>
  The `x-tenant-id` and `x-user-id` headers sent by clients are **ignored and stripped** by the Gateway
  to prevent ownership spoofing. The tenant is determined solely by the authenticated API Key.
</Warning>

## OAuth 2.0

MCP clients can obtain an access token (prefix `mcat_`) through the OAuth 2.0 Authorization
Code + PKCE(S256) flow and pass it the same way in the `Authorization: Bearer mcat_...` header.

- Authorization server (issuer): `{{oauthIssuer}}` — RFC 8414 metadata at {{oauthDiscoveryUrl}}
- Client ID Metadata Documents (CIMD): supported (`client_id_metadata_document_supported: true`) — an HTTPS metadata document URL can be used as the `client_id`, and is the recommended first choice
- Dynamic Client Registration (DCR): POST {{oauthRegistrationUrl}} — registers instantly, no approval step
- Scopes: {{oauthScopes}}
- Protected-resource metadata (RFC 9728): {{oauthPrmUrl}}

## cURL example

```bash
curl -X POST https://mcp.bridger.kr/mcp \
  -H "x-api-key: $BRIDGER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```
