Bridger's **BYOAPI (Bring Your Own API)** lets you register a REST API as an MCP tool on the Bridger
Gateway **without building or deploying a separate container** — as long as you have an OpenAPI spec.

<Note>
  BYOAPI is **live**: any authenticated account API key can register an OpenAPI spec.
  Register via POST {{byoapiRegisterUrl}} and poll progress via GET {{byoapiStatusUrl}}.
</Note>

## Core idea — registration, not deployment

| Approach | Summary |
| --- | --- |
| **Traditional approach** | Build, deploy, and operate one container per API. Both cost and management explode. |
| **Bridger BYOAPI** | Register only the tool definition in the DB. A single Gateway routes by ID, so the tool becomes callable as soon as registration completes. |

```text
A single Bridger Gateway (mcp.bridger.kr)
  ├─ Official preset   tool_id: @datari/weather-ultra-shortcast   → tool: kma_get_ultra_shortcast
  ├─ Official preset   tool_id: @datari/realestate-apt-trade      → tool: molit_get_apt_trade
  ├─ BYOAPI            tool_id: @user123/my-petstore              → tool: listpets, getpetbyid
  ├─ BYOAPI            tool_id: @company/internal-crm             → tool: ...
  └─ ... full preset catalog
```

## Tool names and identifier scheme

Bridger has two registration paths with different identifier schemes.

**1. Official presets** — loaded directly by the Gateway from OpenAPI YAML in `vendor/spec`.

- The **Tool ID** (registry registration ID) follows the `@datari/{category}-{name}` format based on the preset file path. e.g. `@datari/weather-ultra-shortcast`. Discover tool names with `tools/list` at `POST https://mcp.bridger.kr/mcp?activation=all` using your Bridger API key.
- The **tool name** (`tools[].name`) follows `{provider prefix}_{snake_case operationId}` (e.g. `getUltraShortcast` → `kma_get_ultra_shortcast`), matching `^[a-z0-9_-]+$` within 64 chars. You use this name as-is in `tools/call`.

**2. BYOAPI tools** — tools a user registers via `/api/v1/register`.

- The **Tool ID** carries an `@{owner}/{slug}` namespace. e.g. `@user123/my-petstore`, `@company/internal-crm`. If the owner doesn't start with `@`, one is added automatically.
- Individual tool names follow `{tool_id slug}_{snake_case operationId}` — e.g. `listPets` on `@user123/my-petstore` becomes `my_petstore_list_pets`.
- If no category is specified at registration, the default is `byoapi`; if public data is detected, the matching category is applied.

| Type | Identifier format | Example |
| --- | --- | --- |
| Official preset (Tool ID) | `@datari/{category}-{name}` | `@datari/weather-ultra-shortcast` |
| Official preset (tool name) | `{toolPrefix}_{snake_case operationId}` | `kma_get_ultra_shortcast` |
| BYOAPI (tool_id) | `@{owner}/{slug}` | `@user123/my-petstore` |

## Registration pipeline

<Steps>
  <Step title="Ingestion">
    Provide the OpenAPI spec as a URL, file upload, or inline text.
  </Step>
  <Step title="Validation">
    Check spec validity and the number of convertible endpoints, and compute a fitness score (`score`).
    If it's invalid or has no convertible endpoints, it's rejected with `422`.
  </Step>
  <Step title="Generation">
    Convert OpenAPI `paths` into MCP Tool definitions (`name`, `description`, `inputSchema`).
  </Step>
  <Step title="Registration">
    Register in the Tool Registry DB — **no container deployment**.
  </Step>
  <Step title="Ready">
    Immediately exposed in `tools/list` on `mcp.bridger.kr/mcp`; on `tools/call`, the runtime proxy calls upstream.
  </Step>
</Steps>

## Behavior after registration

| Stage | Description |
| --- | --- |
| Tool exposure | Registered tools are included in the `tools/list` response. |
| Call routing | The target API is selected based on the tool ID in the `tools/call` request. |
| Auth injection | Required headers or tokens are injected into the upstream request per the stored auth config. |
| Response normalization | The upstream response is returned in a form that's easy for MCP clients to read. |

## Registration API fields

Registration is two steps: `POST {{byoapiRegisterUrl}}` creates a job, then you poll
`GET {{byoapiStatusUrl}}` for its progress.

### Request body

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `spec_url` | string | one of `spec_url`/`spec_raw` | Public HTTPS URL to fetch the OpenAPI spec (JSON/YAML) from. |
| `spec_raw` | string | one of `spec_url`/`spec_raw` | The spec body passed inline as text. |
| `name` | string | yes | Registration name. |
| `auth` | object | no | Non-secret auth selection. `type` is one of `none`/`apikey`/`bearer`/`oauth2`/`basic`; `credentials` carries `header` (apikey) or `tokenEndpoint` (oauth2). When omitted, the spec's `securitySchemes` are used as-is. |
| `visibility` | string | no | `private` (default) or `public`. |

`auth` never carries secrets. The actual key or token is stored afterwards through the
separate secrets API; see [Auth & security](/en/concepts/auth-and-security).

### Response

`201 Created` — returned as soon as the registration job is queued.

| Field | Description |
| --- | --- |
| `job_id` | Registration job ID. Use it in the status path. |
| `status` | `queued`. |
| `score` | Spec fitness score. |

`GET {{byoapiStatusUrl}}` — job status and result.

| Field | Description |
| --- | --- |
| `job_id` | Registration job ID. |
| `status` | `queued` · an in-progress step · `registered` · `failed` · `cancelled`. |
| `step` | Current pipeline step. |
| `tool_reg_id` | Registered Tool ID (`@{owner}/{slug}`, e.g. `@user123/my-petstore`). Filled in once registration completes. |
| `error` | Failure reason (empty string when there is none). |
| `updated_at` | Last update time. |
