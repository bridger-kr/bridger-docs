Bridger Gateway는 두 가지 인증 헤더를 받습니다. 둘 중 하나만 보내면 됩니다.

```http
x-api-key: dk_live_xxx
Authorization: Bearer dk_live_xxx
```

## API Key 발급

[portal.bridger.kr](https://portal.bridger.kr)의 **브릿저 API 키** 페이지에서 발급/회수합니다.
자세한 흐름은 [API 키 가이드](/guides/api-keys)를 참고하세요.

## 인증 실패 응답

키가 없거나 잘못된 경우 **401 Unauthorized**가 반환됩니다. 본문은 JSON이 아니라
`text/plain` 에러 코드이며, OAuth 클라이언트가 인가 서버·스코프를 찾을 수 있도록
RFC 6750식 `WWW-Authenticate` 챌린지 헤더가 함께 전송됩니다.

```http
HTTP/1.1 401 Unauthorized
Content-Type: text/plain; charset=utf-8
WWW-Authenticate: Bearer error="invalid_token", resource_metadata="https://mcp.bridger.kr/.well-known/oauth-protected-resource/mcp"
```

```text
invalid_token
```

`resource_metadata`는 RFC 9728 보호 리소스 메타데이터를 가리키며, 요청한 MCP
엔드포인트 경로(`/mcp`)가 반영됩니다. 이 메타데이터에서 인가 서버(issuer)와
지원 스코프를 확인한 뒤 [OAuth 2.0](#oauth-20) 인가 코드 + PKCE 흐름을
시작하세요. 유효한 토큰이지만 필요한 스코프가 없으면 같은 챌린지 형식으로
**403 Forbidden**이 반환됩니다 (`Bearer error="insufficient_scope",
resource_metadata="...", scope="..."`).

## 테넌트 식별

테넌트는 **API Key로만** 식별됩니다. 조직 단위로 발급된 키는 해당 조직의 테넌트에
자동으로 연결됩니다.

<Warning>
  클라이언트가 보내는 `x-tenant-id`·`x-user-id` 헤더는 소유권 위조(spoofing)를 막기 위해
  Gateway에서 **무시·제거**됩니다. 테넌트는 인증된 API Key로만 결정됩니다.
</Warning>

## OAuth 2.0

MCP 클라이언트는 OAuth 2.0 Authorization Code + PKCE(S256) 흐름으로 `mcat_` 접두사 access token을
발급받아 동일하게 `Authorization: Bearer mcat_...` 헤더로 전달할 수 있습니다.

- 인가 서버(issuer): `{{oauthIssuer}}` — RFC 8414 메타데이터는 `{{oauthDiscoveryUrl}}`에서 조회
- 클라이언트 ID 메타데이터 문서(CIMD): 지원 (`client_id_metadata_document_supported: true`) — HTTPS 메타데이터 문서 URL을 `client_id`로 사용할 수 있으며, 우선 권장됩니다
- 동적 클라이언트 등록(DCR): POST {{oauthRegistrationUrl}} — 별도 승인 없이 즉시 등록
- 스코프: {{oauthScopes}}
- 리소스 서버 메타데이터(RFC 9728): {{oauthPrmUrl}}

## cURL 예시

```bash
curl -X POST https://mcp.bridger.kr/mcp \
  -H "x-api-key: $BRIDGER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```
